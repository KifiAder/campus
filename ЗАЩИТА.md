# Защита проекта «Биржа проектов»

Шпаргалка на случай вопросов: как устроено, где что лежит, почему сделано именно так
и что отвечать. Номера строк указаны по текущей версии файлов.

---

## 1. Главное за 30 секунд

Одной фразой: **страницы на HTML/CSS/JS общаются с Python-сервером через JSON API,
сервер проверяет права и работает с MySQL через параметризованные запросы.**

Поток данных при регистрации:

```
браузер                сервер (app.py)              база (MySQL)
───────                ───────────────              ────────────
форма → проверка JS →  POST /api/register
                       повторная проверка полей
                       db.create_user()      →      INSERT INTO users
                       пароль → PBKDF2-хеш
                       start_session()  (cookie)
       ← JSON {ok, user}  ← название + Set-Cookie
  редирект на /cabinet
  GET /api/me          →  читает cookie
                          ищет id сессии      →      SELECT FROM users
       ← {user, summary}
```

Три принципа, которые стоит назвать вслух:

1. **Проверки дублируются.** JS — для удобства, сервер — для безопасности.
2. **Пароль нигде не хранится открытым**, в браузер он тоже не возвращается.
3. **Права проверяются на сервере**, а не «спрятанной кнопкой» в интерфейсе.

## 2. Структура и зачем каждый файл

| Файл | Роль |
|---|---|
| `app.py` | HTTP-сервер, маршруты API, сессии, раздача страниц и статики |
| `db.py` | все SQL-запросы + хеширование паролей |
| `schema.sql` | создание БД `campus`, 4 таблиц и тестовых пользователей |
| `templates/*.html` | 8 страниц, в каждой только разметка, данных внутри нет |
| `static/css/style.css` | стили, тёмная тема через CSS-переменные |
| `static/js/app.js` | общий код: `api()`, шапка, тема, утилиты, карточка проекта |
| `static/js/<страница>.js` | логика конкретной страницы |

Почему без фреймворков: стандартный `http.server` + один драйвер MySQL — проект
запускается двумя командами и не зависит от версий Flask/Django. Минус — маршруты
пришлось написать руками, но их всего 11.

## 3. База данных

### 3.1 Четыре таблицы

```sql
users        id, login UNIQUE, password, name, email UNIQUE, role, created_at
projects     id, owner_id → users.id, title, short_desc, body, tags, status, created_at
applications id, project_id → projects.id, user_id → users.id, message, created_at
status_log   id, project_id → projects.id, old_status, new_status, changed_at
```

Почему четыре, а не две из минимума: `application` — это заявка «хочу в проект»,
без неё биржа превращается в доску объявлений; `status_log` — история, потому что
статус меняется, а знать «когда и из чего» полезно (и это мой творческий пункт).

### 3.2 Связи

- `projects.owner_id → users.id` — у проекта один автор, у автора много проектов (**1:N**).
- `applications` — **связующая таблица** между `users` и `projects`, по сути **M:N**:
  один студент участвует во многих проектах, у проекта много откликов.
- `ON DELETE CASCADE` — удалили пользователя, ушли его проекты, отклики и журнал.
- `UNIQUE KEY uq_app_project_user (project_id, user_id)` — **на уровне базы** нельзя
  откликнуться дважды. Если спросят «а если через API два раза?» — сервер вернёт 409,
  а даже если обойти — сработает уникальный индекс.

### 3.3 Пароли

`db.hash_password()` (строка 33), `db.verify_password()` (строка 42).

- Используется **PBKDF2-HMAC-SHA256, 200 000 итераций**, соль случайная
  (`secrets.token_hex(8)`) — у каждого пароля своя.
- В БД лежит строка `pbkdf2_sha256$200000$<соль>$<хеш>`, а не пароль.
- Сравнение через `hmac.compare_digest` — за постоянное время, чтобы нельзя было
  подобрать по времени ответа.
- Зачем итерации: один запуск хеша ~0.04 с для вас и в миллионы раз дольше для
  перебора.

Вопрос «почему не MD5/SHA256 просто так?» — они быстрые, значит перебор миллиардов
вариантов в секунду реален; PBKDF2 намеренно медленный.

### 3.4 Защита от SQL-инъекций

`db.query(sql, params)` (строка 87) вызывает `cursor.execute(sql, params)`.
Драйвер передаёт значения **отдельно** от текста запроса, поэтому `' OR 1=1 --`
в поле логина станет просто строкой-логином и ничего не найдёт.

Что отвечать: «в коде нет ни одной склейки SQL через `+` или f-строку с данными
пользователя — только `%s` и кортеж параметров».

## 4. Сервер: маршруты и обработка запроса

### 4.1 Как устроен один запрос

1. `do_GET` / `do_POST` / `do_PATCH` → `handle_request()` (строка 412).
2. Если путь начинается с `/api/` → `handle_api()` (438), иначе `handle_files()` (460).
3. `handle_api` ищет путь в списке `ROUTES` (371): сначала все совпадения по шаблону,
   потом поиск нужного метода. Если путь есть, а метода нет — **405**, если пути нет — **404**.
4. Обработчик возвращает словарь → `send_json()` (506) сериализует его в JSON.

### 4.2 Все маршруты (11 штук)

| Метод | Путь | Функция | Доступ |
|---|---|---|---|
| POST | `/api/register` | `api_register` | все |
| POST | `/api/login` | `api_login` | все |
| POST | `/api/logout` | `api_logout` | все |
| GET | `/api/me` | `api_me` | все |
| GET | `/api/projects` | `api_projects_list` | все |
| POST | `/api/projects` | `api_project_create` | вход |
| GET | `/api/projects/<id>` | `api_project_get` | все |
| PATCH | `/api/projects/<id>/status` | `api_project_status` | автор/куратор |
| POST | `/api/projects/<id>/apply` | `api_apply` | вход |
| GET | `/api/applications` | `api_my_applications` | вход |
| GET | `/api/applications/sent` | `api_my_sent` | вход |

### 4.3 Ошибки: один класс на всё

`ApiError` (48) хранит текст и HTTP-код. В `handle_request` он перехватывается и
превращается в `{"error": "..."}` с нужным статусом.

- **400** — битый JSON; **401** — не вошёл / неверный пароль;
- **403** — вошёл, но нельзя (чужой проект); **404** — нет объекта;
- **409** — конфликт (занят логин, повторный отклик); **422** — не прошла валидация;
- **503** — база недоступна; **500** — прочее (с записью в консоль).

## 5. Вход, сессия и права

### 5.1 Что происходит при входе

`api_login` (128):

1. Берём логин и пароль, проверяем, что не пустые.
2. `find_user_by_login` — `SELECT * FROM users WHERE login = %s`.
3. `db.verify_password(пароль, user["password"])`.
4. На **любую** неудачу одно сообщение: «Неверный логин или пароль» — чтобы не
   подсказывать, какие логины существуют (защита от перебора логинов).
5. `start_session()` (349): генерирует `secrets.token_urlsafe(24)` → кладёт в словарь
   `SESSIONS[sid] = user_id` и отдаёт cookie `session` с флагами
   **HttpOnly** (JS не украдёт) и **SameSite=Lax**.
6. `public_user()` (82) вырезает хеш пароля — клиенту уходит только имя, логин, роль.

### 5.2 Как сервер понимает, кто вошёл

`current_user` нет — есть `get_user(handler)` (333): читает cookie, берёт `user_id`
из `SESSIONS`, повторно грузит пользователя из БД. `get_user_or_error` (341) —
то же, но без сессии бросает `ApiError(401)`.

Почему данные берутся из БД, а не из cookie: cookie — это только «ключик». Роль
(student/curator) всегда читается актуальная, её нельзя подделать.

### 5.3 Где именно проверяются права

| Что защищаем | Код | Ответ |
|---|---|---|
| Создание проекта | `get_user_or_error` в `api_project_create` (204) | 401 |
| Смена статуса | `if user["role"] != "curator" and project["owner_id"] != user["id"]` (235) | 403 |
| Отклик на свой проект | `api_apply` (257) | 403 |
| Отклик в закрытый проект | `api_apply` (259) | 409 |
| Страница `/cabinet` без входа | `handle_files` (467) | редирект на `/login` |
| Страница `/admin` не куратору | `handle_files` (469-471) | 403 |

Ключевая фраза: «если студент вручную введёт `/admin`, он получит 403 — проверка стоит
в `handle_files`, а данные в API тоже защищены отдельно, чтобы нельзя было обойти
через прямой запрос к `/api/...`».

### 5.4 Выход

`api_logout` → `end_session` (357): удаляет id из `SESSIONS` **на сервере** и отдаёт
cookie с `Max-Age=0`. Даже если браузер оставит старую cookie, сервер её уже не узнает.

## 6. Фронтенд: JavaScript

### 6.1 Один хелпер на все запросы

`api(method, url, body)` в `static/js/app.js` (5): `fetch` с JSON, проверка `response.ok`,
при ошибке бросает `Error` с текстом из `{error}` сервера. Поэтому во всех страницах
одинаковый `try/catch` — и в `catch` всегда человеческий текст, а не «Failed to fetch».

### 6.2 Валидация: правила одни на всю систему

`register.js` строки 4–6 повторяют константы `app.py` 42–44:

- логин `3–20`, латиница/цифры/`_`/`.`;
- пароль `не короче 6`;
- e-mail по регулярке; имя `от 2 символов`; пароли совпадают.

Порядок в `register.js`:

1. `blur` поля → проверка → сообщение под полем (`setFieldError`).
2. `submit` → перепроверяем **все** поля; если хоть одно «нет» — `return`,
   запрос на сервер **не уходит**.
3. Кнопка `disabled` + текст «Создаём…» — защита от двойного клика.
4. Успех → зелёное сообщение и переход в кабинет; `409` → подсветка поля логина.

### 6.3 Почему проверок две

«JS можно отключить в консоли браузера или отправить запрос через curl — поэтому те же
правила есть в `api_register` (строки 104–118: сборка словаря `errors` и `if errors:
raise ApiError(..., 422)`). JS нужен для UX, сервер — для безопасности.»

### 6.4 Экранирование

Всё, что пришло из БД, перед вставкой в HTML проходит через `esc()` (`app.js` 31):
`<` превращается в `&lt;`. Иначе пользователь мог бы вписать в описание проекта
тег `<script>` и сломать страницу (XSS). Текст выводится через `esc(project.title)`,
а не «как есть».

## 7. Что происходит при каждом действии

Это удобно проговорить, если попросят «покажи и объясни по ходу».

### Регистрация (Логин → «Создать аккаунт»)

1. JS: все поля проверены, ошибок нет.
2. `POST /api/register` → `api_register` (96): те же проверки ещё раз, `clean()`
   обрезает пробелы и длину, e-mail приводится к нижнему регистру.
3. `db.create_user` → `INSERT`; `login`/`email` уникальны в БД → повтор даёт
   `ER_DUP_ENTRY` → возвращаем `None` → ответ **409**.
4. `start_session` — пользователь сразу авторизован (не надо входить второй раз).

### Публикация проекта (Кабинет → «Опубликовать»)

1. `POST /api/projects` → `api_project_create` (202), нужен вход.
2. Пороги: заголовок ≥ 6, короткое описание ≥ 10, подробное ≥ 30 символов.
3. `INSERT INTO projects (owner_id, ...)`, `owner_id` берётся из **сессии**, а не из
   тела запроса — подставить чужой id нельзя.
4. Ответ: проект + сообщение; JS переключается на вкладку «Мои проекты».

### Отклик (страница проекта → «Отправить отклик»)

1. `POST /api/projects/<id>/apply` → `api_apply` (250): не свой проект, статус `open`,
   сообщение от 15 символов.
2. Вставка в `applications`; повторный отклик ловится уникальным ключом → **409**.
3. Автор видит отклик в кабинете → «Входящие заявки» (`GET /api/applications`).

### Смена статуса (страница проекта, `/admin`)

1. `PATCH /api/projects/<id>/status` → `api_project_status` (229): проверка
   «автор или куратор», затем `new_status` сверяется с `STATUSES`.
2. `db.update_project_status` (184) делает **две** операции: `UPDATE projects` и
   `INSERT INTO status_log` — статус и история не расходятся.
3. Если статус тот же — возвращается `changed = False`, в журнал ничего не пишется.

### Поиск и фильтр (`/board`, «Мои проекты»)

`db.list_projects` (149) собирает SQL по условиям: `status` проверяется по белому
списку, поиск — `LIKE %...%` по названию/описанию/тегам, `mine=1` добавляет
`AND p.owner_id = ?`. Данные всегда через `params`, не через склейку.
(Ручка, которая это вызывает, — `api_projects_list`, строка 144.)

### Счётчики в кабинете

`db.user_summary` (265): обычному студенту считает только его проекты и отклики,
куратору — по всей бирже (`COUNT(*)` с `JOIN`).

## 8. Вопросы, которые чаще всего задают

**«Где у тебя пароль?»**
В `users.password` — хеш `pbkdf2_sha256$...`. Пароль открытым текстом не хранится и
из API не возвращается (`public_user`).

**«Можно ли зайти под другим логином, поменяв cookie?»**
Cookie — случайная строка `token_urlsafe(24)`, сервер ищет её в `SESSIONS`. Подбор
практически невозможен, а при выходе запись удаляется.

**«Что будет, если дважды откликнуться?»**
Кнопка отправит второй запрос, сервер вернёт 409 с текстом «Вы уже откликались»,
JS покажет его в блоке уведомления. На уровне БД это ещё и `UNIQUE`-ключ.

**«Почему сервер не хранит пароль в сессии?»**
В сессии только `user_id`. Это меньше данных и невозможно «забыть» обновить роль.

**«Почему при неверном логине и при неверном пароле одно сообщение?»**
Чтобы нельзя было выяснить, существует ли логин — такова практика аутентификации.

**«Что мешает верстать без сервера (localStorage)?»**
По заданию нужна именно БД: данные должны переживать закрытие браузера и быть
видны другим пользователям — у автора и куратора одновременно.

**«Где адаптив?»**
`style.css` — медиазапрос `max-width: 760px`: навигация переезжает под логотип,
сетка становится в одну колонку, таблицы превращаются в карточки. Проверено на 390px.

**«Как хранится тема?»**
`localStorage["theme"]` + атрибут `data-theme` на `<html>`; цвета — CSS-переменные,
поэтому вторая тема — это ~15 строк, а не второй css-файл.

**«Почему `ThreadingHTTPServer` и `Lock`?»**
Сервер обрабатывает запросы в разных потоках; `SESSIONS_LOCK` не даёт двум потокам
одновременно менять словарь сессий (иначе возможны сбои при редких совпадениях).

**«Что бы ты улучшил?»**
Честный ответ, а не «всё идеально»:
- сессии в памяти — после перезапуска сервера нужен повторный вход (в учебном
  варианте это допустимо; в реальном проекте — Redis или таблица `sessions`);
- нет пагинации — при сотнях проектов понадобится `LIMIT/OFFSET`;
- нет сброса пароля и подтверждения e-mail;
- проект нельзя отредактировать или удалить после публикации.

## 9. Мини-демо на защите (2 минуты)

1. `/register` → «Создать аккаунт» с пустыми полями — ошибки под полями, **запрос не ушёл**
   (это видно во вкладке Network).
2. Заполнить, зарегистрироваться → попадаете в кабинет.
3. Опубликовать проект → он в «Моих проектах» и на `/board`.
4. Выйти, войти как `timosh / student123`, откликнуться на ваш проект.
5. Войти как `curator / admin123` → «Куратор» → сменить статус в таблице.
6. Открыть проект: в «Истории статусов» появилась строка.
7. Переключить ☾ — тёмная тема; сузить окно до 390px — адаптив.

Если спросят «покажи в базе» — в MySQL:

```sql
SELECT id, login, role, LEFT(password, 30) AS password_hash FROM users;
SELECT id, title, status, owner_id FROM projects;
SELECT * FROM applications;
SELECT * FROM status_log;
```

Хеш в первой строке — лучший аргумент, что пароль не лежит открытым текстом.
